# Debezium 3.6 RPS Upgrade Design

## Goal

Move RPS from its mixed Debezium 3.0.3 runtime to one internally controlled Debezium 3.6.2 release without losing custom MySQL, MariaDB, GoldenDB, TDSQL, or Oracle behavior, and prove offset and schema-history continuity before production rollout.

## Baseline

- Source baseline: `v3.0.3.Final` plus the three internal source lines recorded in `docs/rps-migration/debezium-customization-inventory.yaml`.
- Target baseline: released tag `v3.6.2.Final` at `02810e25b19c04e5095b2b6fbbdcbae549a69f19`.
- Implementation branch: `upgrade/debezium-3.6.2-rps`.
- The unreleased tip of `upstream/3.6` is not an implementation baseline.
- Existing 3.0.3 worktree files and untracked migration evidence remain untouched.

## Migration Rule

The migration unit is a testable behavior, not a dated artifact or Git commit. For each behavior, adapt its regression test to clean 3.6.2 first. A passing behavior is classified `UPSTREAM` and its old production patch is not copied. A failing required behavior is classified `REBASE` and reimplemented against the current 3.6 module/API. Dependencies on removed APIs or the old binlog client are classified `REDESIGN`.

## Workstreams

1. Complete the source, RPS history, and Nexus artifact inventory.
2. Establish a clean 3.6.2 compile and unit-test baseline with JDK 21.
3. Qualify later-upstream backports by moving tests before production code.
4. Rebase GoldenDB/TDSQL grammar behaviors in independent parser changes.
5. Redesign compressed binlog event support against the 3.6 client API.
6. Rebase bounded CDC diagnostics and timestamp metadata against connector-common.
7. Rebase Oracle `txName` and Oracle 10g behavior as an independent release unit.
8. Align the complete RPS dependency graph and eliminate mixed Debezium runtimes.
9. Run old-state continuation, contract comparison, performance, canary, and rollback exercises.

## Release Shape

Only components whose production code differs from upstream use independent
dated versions. The release imports the official `3.6.2.Final` BOM and
overrides the six changed Debezium modules plus the custom binlog client in
`debezium-rps-custom-bom:3.6.2-20260916.Final`. RPS may not combine this line
with any Debezium `3.0.3*` runtime implementation.

Only one Oracle connector implementation may be present on the runtime
classpath. IBM i uses its official `3.6.2.Final` connector and transitive
components.

## Verification Gates

- G0: Every deployed dated artifact maps to a checksum, source commit, capability, and RPS consumer.
- G1: Clean 3.6.2 affected-module build and unit baseline passes with executed-test counts.
- G2: Every capability has an evidence-backed `UPSTREAM`, `REBASE`, `REDESIGN`, or approved `RETIRE` decision.
- G3: The RPS dependency tree has no Debezium 3.0.3 runtime and no duplicate connector classes.
- G4: Transferred to product test regression: old offset, schema-history, and
  checkpoint continuation.
- G5: Transferred to product test regression: contract and supported-source
  acceptance. Live MariaDB V2 events 169-171 are explicitly waived for this
  code upgrade without being claimed as passed.
- G6: Transferred to product test regression: shadow/canary, performance,
  failure injection, and rollback rehearsal.

## Closure decision

The code migration and release scope is closed by
`docs/rps-migration/upgrade-closure-2026-09-16.md`. G4-G6 remain product
quality gates, but are not incomplete implementation tasks on the 3.6.2
upgrade branch.

## Stop Conditions

- An internal Nexus artifact cannot be mapped to source.
- A test cannot distinguish old behavior from the requested behavior.
- A change requires copying a 3.0.3 module architecture into 3.6.
- Dependency convergence leaves any duplicate Debezium connector implementation.
- Offset or schema-history continuation produces unexplained loss, duplication, or schema drift.

Commits, branch publication, Nexus publication, and RPS dependency alignment
were subsequently authorized and completed. Production deployment remains
outside this repository's implementation scope.
